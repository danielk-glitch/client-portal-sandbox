# Transaction portal components

`types.ts` defines content shared by seller and buyer transaction views. `components/` owns the visual treatment of people, dates, activity, tasks, advertising, feedback, notes, documents, and detail sections. Import those components through `components/index.ts`.

Pages own route state, the transaction data they display, and actions such as opening a document. `SellerPortal` currently supplies those values and accepts `transaction` and `basePath` props, so a second seller view can use different sample data and its own listing URL while sharing the same presentation. A buyer page can compose the shared components without importing seller data.

The central component gallery keeps portal examples together in its collapsed **Portal patterns** section. Add new portal-specific examples there rather than giving each row a separate gallery entry.

Internal review and preview tools live in `src/internal`, separate from consumer components. The sandbox seller page explicitly mounts `SellerReviewTools`; this integration is for prototype review and must be omitted from the production product. See `src/internal/README.md` for the folder boundary.

The feedback toolbar’s View menu selects `?view=before-listing` or `?view=under-contract`, independently of layout controls. `src/internal/review/sellerJourneyViews.ts` supplies a preparation scenario derived from the page’s transaction, preserving its property, team, and branding. Before listing replaces marketing with `ListingPreparation`, supplies preparation-specific content, and opens a private listing preview. View changes preserve design settings and annotation state, clear open transaction details, and participate in browser history. The initial/default view is Under contract. Dates are illustrative scenario snapshots, not today’s schedule.

Future seller views supply optional `resources` and `UpcomingDate.guidance` content. `ResourcesPanel` groups the authored guides by relevance; `DateEventRow` makes guided dates clickable to open meaning and preparation advice in a small `PlaceModal` through `MilestoneExplanation`. An optional related-resource chip sits on the right on desktop and below the description on phones; that chip and the modal’s guide action use `ResourceGuideSheet` and the shared `PlaceSheet` bottom drawer used by listing details. The guide reader has an editorial title, desktop section navigation, numbered preparation advice, and a distinct questions section. Its hamburger opens a resource library inside the sheet, listing all resources supplied by the current transaction and highlighting the current guide. Selecting another resource closes the library, resets the reading position, and focuses the new title. Navigation scrolls within the sheet and moves focus to the selected section. Relevance is authored sample data in this prototype. The original seller view has no resources or milestone guidance.

`DocumentsPanel` displays preview cards, with pinned documents above the paginated remainder. Pass a viewer-and-transaction-specific storage key and remount with a matching React key if that scope changes. Pin preferences are stored locally in the browser. `DocumentCard` accepts `thumbnailUrl` for a real preview image; sample documents without attached files display a page illustration built from their metadata. Cards show the title, uploadedAt date, and byline; clicking a card opens the document.

Team client preview renders the existing `SellerPortal` with `readOnly` and `showReviewTools={false}`. `DocumentsPanel` and `DocumentCard` accept `readOnly` to disable pin changes while allowing reading. Rich-text resource sections accept optional sanitized `html`; custom guides omit the questions section when none are supplied.

# Transaction portal components

`types.ts` defines content shared by seller and buyer transaction views. `components/` owns the visual treatment of people, dates, activity, tasks, advertising, feedback, notes, documents, and detail sections. Import those components through `components/index.ts`.

Pages own route state, the transaction data they display, and actions such as opening a document. `SellerPortal` currently supplies those values and accepts `transaction` and `basePath` props, so a second seller view can use different sample data and its own listing URL while sharing the same presentation. A buyer page can compose the shared components without importing seller data.

These kit components aren't in the component gallery. Generic building blocks they use, such as `PortalSectionHeader`, `PortalIconBadge`, `AgentIdentity`, and `PartnerBrandLockup`, live in `src/components` and are in the gallery.

Internal review and preview tools live in `src/internal`, separate from consumer components. The sandbox seller page explicitly mounts `SellerReviewTools`; this integration is for prototype review and must be omitted from the production product. See `src/internal/README.md` for the folder boundary.

The feedback toolbar’s View menu selects `?view=before-listing`, `?view=listed`, or `?view=under-contract`, independently of layout controls. Listed (`createListedTransaction`) keeps the transaction’s marketing and showings, marks the home Active, swaps in listed-stage dates and tasks, and is the only view with the Market activity block (a side-scrolling carousel of nearby competing homes, mock data in `seller-portal/market-activity`). `src/internal/review/sellerJourneyViews.ts` supplies a preparation scenario derived from the page’s transaction, preserving its property, team, and branding. Before listing replaces marketing with `ListingPreparation`, supplies preparation-specific content, and opens a private listing preview. View changes preserve design settings and annotation state, clear open transaction details, and participate in browser history. The initial/default view is Under contract. Dates are illustrative scenario snapshots, not today’s schedule.

Future seller views supply optional `resources` and `UpcomingDate.guidance` content. `ResourcesPanel` groups the authored guides by relevance; `DateEventRow` makes guided dates clickable to open meaning and preparation advice in a small `PlaceModal` through `MilestoneExplanation`. An optional related-resource chip sits on the right on desktop and below the description on phones; that chip and the modal’s guide action use `ResourceGuideSheet` and the shared `PlaceSheet` bottom drawer used by listing details. The guide reader has an editorial title, desktop section navigation, numbered preparation advice, and a distinct questions section. Its hamburger opens a resource library inside the sheet, listing all resources supplied by the current transaction and highlighting the current guide. Selecting another resource closes the library, resets the reading position, and focuses the new title. Navigation scrolls within the sheet and moves focus to the selected section. Relevance is authored sample data in this prototype. The original seller view has no resources or milestone guidance.

`DocumentsPanel` displays preview cards, with pinned documents above the paginated remainder. Pass a viewer-and-transaction-specific storage key and remount with a matching React key if that scope changes. Pin preferences are stored locally in the browser. `DocumentCard` accepts `thumbnailUrl` for a real preview image; sample documents without attached files display a page illustration built from their metadata. Cards show the title, uploadedAt date, and byline; clicking a card opens the document.

Team client preview renders the existing `SellerPortal` with `readOnly` and `showReviewTools={false}`. `DocumentsPanel` and `DocumentCard` accept `readOnly` to disable pin changes while allowing reading. Rich-text resource sections accept optional sanitized `html`; custom guides omit the questions section when none are supplied.

`UpcomingDate.guidance.links` attaches web links to a date. `MilestoneExplanation` lists them under a Links heading with `DocumentListRow` (link icon, website title, URL underneath, outward arrow, opens in a new tab). Links never show as a chip on the date row. The team Dates editor adds, edits, and removes them.

Market activity uses photo-led property cards with native horizontal scrolling, scroll snapping, previous/next controls, and keyboard arrow support. It sits directly below listing performance in Future v1, the timeline exploration, and Latest Vision (`/seller/v1-iteration2`). Each card opens the shared `ListingDetailsSheet` with nearby-home data: its photo, price, status, property highlights, distance, and market-change facts. Sold and withdrawn homes use sale-price and last-asking-price labels. Subject-only publishing badges, agent branding, and unavailable details are omitted. All layouts use the same mock data and summary counts.


All file entry points use `DocumentViewer`: document cards, staged lists, and timeline attachments in the seller portal, team client preview, timeline-first layouts, and hero explorations. `DocumentPreviewModal` remains an alias for callers using the old name. `TransactionDocument.fileUrl` can point at the attached PDF; prototype samples otherwise resolve to `/documents/<id>.pdf`. `fileName` is optional. Team-authored rich-text guides in the dashboard's separate Resources tab continue using `ResourceGuideSheet`.

Pass the same `useDocumentPins` result to a viewer and its `DocumentsPanel` (via `pins`) or staged list (`pinnedIds`) to keep pin changes in sync. Team client preview omits the viewer's pin action. Structured documents add linked-date details via `clientDocumentFacts`; the viewer omits stage metadata.

Timeline rows representing an available document open that document directly in `DocumentViewer`, without a step-details dialog. Date rows and documents not yet shared retain their explanatory details.


`DocumentViewer` uses a shadowbox: a fading 6px blur and dim backdrop over the portal, floating PDF pages, and one floating bottom bar for title, details, page position, zoom, download, pin, and close. Secondary information appears in an info tooltip on hover, keyboard focus, or tap. Below 768px the bar uses two compact rows, with an icon for download. Initial fit respects both reader width and height; larger zoom levels scroll within the reader. Backdrop click and Escape close the dialog and restore focus. The 240ms entrance and 180ms exit respect reduced-motion; reduced-transparency removes the blur.

`EmailsPanel` is the Emails tab on Latest Vision (`/seller/v1-iteration2`). It lists emails collected from the transaction's cc/bcc address (for example `listingagent+transaction003@…`), grouped into threads, newest first. Every collected email shows to the client; there is no curation step. A row opens a modal with threads on the left and the selected thread's messages on the right (one pane at a time below 768px). Attachments show as file chips and do not open yet. Sample data lives in `emailsData.ts`; `TransactionEmail` is in `types.ts`.
